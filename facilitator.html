Run sheet (60 minutes)

  1. 0–5 min: brief. Teams of 3–5 open the student page on one device each. Explain the story: they are developers at a games studio, building a Rock Paper Scissors game from six tickets. Each ticket is one function with automatic tests. Point out the choice of code blocks or Python, and that the game panel switches on as they complete stages.
  2. 5–7 min: the AI comparison. Explain the “Compare with AI” panel: after passing a stage, they ask an AI for the same function, test its code, and give a verdict for bonus points. The simulated assistant, Pixel, is selected by default for schools where chatbots are blocked or not allowed. Pixel deliberately makes realistic mistakes: its first answer is usually wrong, even for a good prompt, and it explains its code confidently either way. Teams should test its code, then tell Pixel what went wrong and ask again. Ask them to write their own prompts rather than pasting the whole specification every time.
  3. 7–50 min: sprint. Start the countdown. Circulate and help. Most teams finish stages 1–4 in 25–30 minutes. Stage 5 and the stage 6 strategy tournament stretch stronger teams. Hints cost 15 points each.
  4. 50–52 min: codes. Teams press “Finish and get code” and read out their team name and code. Add them to the leaderboard and switch to projector view.
  5. 52–60 min: debrief. Use the prompts below, then the course and careers slide.

Scoring

  • Stages 1–5: 100 points each.
  • Stage 6: 60 points, plus 10 for each of the five bots beaten (beating 3 passes).
  • Each hint: −15 points.
  • AI comparison with a verdict: +25 points per stage.

Debrief prompts

  • Why we still need human developers. Pixel's first answer was wrong in almost every stage, even when the prompt was good. Who spotted the mistake by reading the code, and who only found it from the tests? What would have happened if you'd trusted the AI and shipped its code?
  • Confident but wrong. Pixel said things like “this handles draws” and “this works for any match length” when the code didn't. Did anyone believe an explanation that turned out to be false? Where could a confident wrong answer cause real harm, for example in banking, medical or security software?
  • Specifications. Who saw "Win" instead of "win", None instead of False, or "Spock" instead of "spock"? Why does a computer care about differences a person wouldn't notice?
  • Subtle bugs. In stage 3, checking text in "rock paper scissors" instead of a list lets empty text through. In stage 4, best_of // 2 is out by one. Why are bugs that are one character long so easy to miss, and why do they matter most in input validation?
  • Testing. Most of Pixel's wrong answers still passed most of the tests. Is passing a few tests proof that code works? Who writes tests in a real team, and when?
  • Prompting. Which teams told Pixel what went wrong and got a better answer? What details made the difference? Did it ever take more than one try?
  • Maintainability. How much code did you change to add lizard and Spock? Did teams that used a dictionary or list have an easier time than teams with many if statements?
  • Your own AI. Your stage 6 strategy predicts the next move from past data. How is that like, and unlike, the chatbot you used?
  • Careers. Developers now use and review AI-written code every day. Which skills from today, such as reading code, testing and spotting edge cases, would make you good at that job?

Troubleshooting

  • “Python didn't load”. The page downloads Python from cdn.jsdelivr.net and code blocks and the editor from cdn.jsdelivr.net and cdnjs.cloudflare.com. Ask the school's IT team to allow these, and test on the school network before the session.
  • First load is slow. Python takes 5–20 seconds to start the first time. Ask teams to open the page during the brief.
  • “Ran for too long”. A loop never ends. The page stops it automatically; the team needs to fix the loop.
  • Blocks look odd in Python. Blockly sometimes adds global lines when a variable is used inside a function. This is normal and the code still works.
  • Lost progress. Progress is saved in the browser on that device. Opening the page in a private window, or on a different device, starts again.
  • Starting fresh on a shared device. Clear the site data for the page in the browser settings, or open it in a new private window.
  • Code not accepted. Check the team name spelling. Codes are tied to the exact team name and score.

Model solutions

For helping stuck teams. Many other solutions are just as good.

Stage 1: beats
def beats(a, b):
    if a == "rock" and b == "scissors":
        return True
    if a == "scissors" and b == "paper":
        return True
    if a == "paper" and b == "rock":
        return True
    return False
Stage 2: round_result
def round_result(player, computer):
    if player == computer:
        return "draw"
    elif beats(player, computer):
        return "win"
    else:
        return "lose"
Stage 3: clean_move
def clean_move(text):
    text = text.strip().lower()
    if text == "r":
        text = "rock"
    elif text == "p":
        text = "paper"
    elif text == "s":
        text = "scissors"
    if text in ["rock", "paper", "scissors"]:
        return text
    return None
Stage 4: match_winner
def match_winner(player_score, computer_score, best_of):
    needed = best_of // 2 + 1
    if player_score >= needed:
        return "player"
    elif computer_score >= needed:
        return "computer"
    else:
        return None
Stage 5: beats with lizard and Spock
def beats(a, b):
    wins_against = {
        "scissors": ["paper", "lizard"],
        "paper": ["rock", "spock"],
        "rock": ["lizard", "scissors"],
        "lizard": ["spock", "paper"],
        "spock": ["scissors", "rock"],
    }
    return b in wins_against[a]
Stage 6: choose_move (beats 4 of 5 bots)
def choose_move(history):
    if len(history) == 0:
        return "paper"
    last = history[-1]
    if last == "rock":
        return "paper"
    elif last == "paper":
        return "scissors"
    else:
        return "rock"

For reference: always playing one move or playing randomly beats at most 2 bots, and the simulated assistant's “most common move” strategy beats 3. A strategy that predicts the opponent's next move from their last two moves can beat all five.
